<objective>
Complete the phase's third and last edit type: an Atendente/Gestor corrects a customer's name or CPF after the cadastro was created, with the same who/when/before/after audit trail already proven for OS contact (02-01) and device credential (02-02).

Unlike the other two, EDIT-03 has no existing write path at all — `create_customer` is creation-only, and nothing in the counter UI edits an existing Customer's identity. This plan builds the missing endpoint on the exact shape of its sibling verb, wires a minimal counter affordance, and surfaces the audit indicator on the customer card.

Purpose: EDIT-03 requires "Dados do cliente (nome/CPF) podem ser corrigidos, com log de auditoria". D-05 locks the gate to the same `CHECKIN_ALLOWED_ROLES` used everywhere else at the counter. D-04 locks the audit content: name and CPF are ordinary PII already visible to Atendente/Gestor, so unlike the device credential they are captured for real — the masking discipline from 02-02 must NOT be over-applied here. D-06 locks the evidence model: no justification field. The one open discretionary question from CONTEXT.md — whether to reuse `validate_customer_contact_document` as-is or wrap it — is resolved here as wrap, because the validator demands a full record and this endpoint accepts a partial one.

Output: an `update_customer` whitelisted endpoint, a `customer_audit` key on the OS detail payload, a `balcao.updateCustomer` TS helper, a counter edit affordance on the Entrada screen, and EDIT-03 assertions in `run_edit_audit_checks()`.
</objective>
