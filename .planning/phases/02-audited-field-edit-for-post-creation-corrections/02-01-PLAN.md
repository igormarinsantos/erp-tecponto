<objective>
Ship the first fully-audited post-creation correction end to end: an Atendente/Gestor edits the OS contact name/phone on an already-created OS, the change is recorded in the existing `Tecponto Access Audit` doctype against the Service Order (not against a User), and the OS detail screen shows who edited it and when.

This is the tracer slice for the whole phase. It touches every layer the phase will modify — doctype schema, the audit-writing service in `user_access.py`, the whitelisted RPC in `api.py`, the detail serializer, the TypeScript contract, the React surface, and the `run_*_checks` test suite — on ONE path only (contact fields). Phases 02-02 (device credential, EDIT-02/EDIT-04) and 02-03 (customer identity, EDIT-03) expand horizontally from the infrastructure proven here.

Purpose: EDIT-01 requires "log de auditoria (quem/quando/antes/depois), reusando o padrão `Tecponto Access Audit`". D-01 locks the mechanism: extend the existing doctype, do not build a parallel one. D-06 locks the evidence model: the automatic before/after snapshot is the record — no typed justification field, because a field correction is not a policy exception like `courtesy_warranty`.

Output: a migrated `Tecponto Access Audit` schema, a widened `_write_audit` plus two new public helpers in `user_access.py`, audit wiring inside `update_service_order_entry`, an `entry_audit` field on the OS detail payload, a React indicator, and `run_edit_audit_checks()` wired into the foundation suite.
</objective>

  <action>
Present this decision to the developer and WAIT for an explicit go/no-go before touching any file.

What is about to change in `tecponto_access_audit.json`:
1. `affected_user` loses `"reqd": 1`. It stays a `Link` to `User`, stays `in_list_view`, stays `read_only`. Every existing row keeps its value; only future rows may omit it.
2. Two new fields are added: `reference_doctype` (`Link` → `DocType`) and `reference_name` (`Dynamic Link` → `reference_doctype`), both `in_list_view` and `read_only`.
3. `field_order` grows from 6 to 8 entries.
4. `permissions` is NOT touched — the doctype stays `System Manager`-only for read/report/export/print.
5. `track_changes` stays `0`.
6. `hooks.py` is NOT touched — `validate_access_audit_immutable` and `prevent_access_audit_deletion` bind by doctype name and already cover any row regardless of which fields it carries.

Why this is one-way: the audit doctype is immutable by design. After the first EDIT-01 row lands with an empty `affected_user`, re-imposing `reqd=1` would make that row invalid and un-fixable (the immutability hook forbids editing it, `prevent_access_audit_deletion` forbids removing it). The relaxation is therefore permanent for the life of the site.

What is deliberately NOT changing, so the developer can confirm the blast radius: no new permission role gains read access to the raw audit log; no existing row is rewritten or backfilled; no data patch is added to `tecponto_app/patches.txt` (a JSON-only field addition plus a `reqd` relaxation is picked up by `bench migrate`'s doctype sync — the two existing patches under `[post_model_sync]` are data-backfill patches, a different category).

Alternative that was considered and rejected by D-01: a second, parallel audit doctype scoped to documents. Rejected because it duplicates the immutability hooks, the permission model, and the writer, and because EDIT-01's own wording says "reusando o padrão `Tecponto Access Audit`".

Ask the developer explicitly: approve migrating the shared audit doctype as described, or stop and re-open the mechanism decision.
