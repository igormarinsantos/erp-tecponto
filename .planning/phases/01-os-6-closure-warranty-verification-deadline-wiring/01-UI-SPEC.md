## Scope & Integration Points

This phase's frontend surface is narrow and additive only — **no new design system, no new visual
language.** One new form control plus its read-only reflections on existing surfaces:

| # | Surface | Status | File / Line |
|---|---------|--------|-------------|
| 1 | Deadline input (Técnico sets `estimated_deadline`, pre-filled, editable) | **NET NEW** | `frontend/src/App.tsx` — inside `TechnicalBudgetEditor` (~line 4122–4165), rendered from the "Diagnosticado — aguardando orçamento" + `pricing_responsibility === "Técnico"` branch (`App.tsx:4012`) |
| 2 | Kanban card display | **NET NEW** | `frontend/src/ServiceOrderKanban.tsx` — `KanbanCard` (line 499–566), `CardLine` list at line 544–549 |
| 3 | OS detail view display | **NET NEW** | `frontend/src/App.tsx` — `ServiceOrderPersistentOverview` (line 4451–4472), inside the existing `{open ? ... : null}` expanded block at line 4468 |
| 4 | Public tracking page display | **ALREADY IMPLEMENTED** — no frontend work | `tecponto_app/public/js/tracking.js:104` already renders `order.estimated_deadline` under the "Previsão" label, with `order.approval_deadline` as fallback. `tracking.py:154` already serializes `estimated_deadline` in `get_public_portal`. Backend only needs to start writing a non-empty value — this vanilla-JS server-rendered page (not part of the React SPA) needs zero UI changes. |
| 5 | Print formats (orçamento / orçamento discriminado) | **ALREADY IMPLEMENTED** — no frontend work | `tecponto_app/tecponto/service_order/print_formats.py:587,647` already render `<strong>Prazo estimado:</strong> {{ tp.estimated_deadline }}`. Backend only needs to populate the field. |

Because surfaces 4 and 5 require zero UI change, this contract governs only surfaces 1–3. Backend
work (new write endpoint, adding `estimated_deadline` to `ServiceOrderSummary`/`ServiceOrderDetailResponse`
serialization) is out of this UI-SPEC's scope — see `01-CONTEXT.md` canonical refs.

**Naming collision warning for the planner/executor:** `ServiceOrderSummary.stage_clock.estimated_deadline`
(`frontend/src/api/types.ts:426`) is an unrelated per-stage SLA clock value with the same field
name. The OS-level field this phase wires is a **new top-level** `estimated_deadline` on
`ServiceOrderSummary` and `ServiceOrderDetailResponse` — do not read from `stage_clock.estimated_deadline`
for surfaces 2–3. Also do not confuse with `approval_deadline` (the unrelated 48h quote-validity
deadline already displayed as "Prazo atual" / "Prazo" at `App.tsx:4468` and `App.tsx:6694`) — the
new field gets its own distinctly-labeled row, per D-06.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline padding |
| sm | 8px | Compact element spacing (`gap-2`) |
| md | 16px | Default element spacing (`gap-3`/`p-4`≈12-16px band) |
| lg | 24px | Section padding |
| xl | 32px | Layout gaps |
| 2xl | 48px | Major section breaks |
| 3xl | 64px | Page-level spacing |

Exceptions: the app uses Tailwind's native 4px-increment scale throughout (e.g. `p-5`=20px on
`Card`, `gap-3`=12px between `TechnicalBudgetEditor` fields) — these are pre-existing, already
multiples of 4, and this phase's new elements (input, Kanban row, DetailLine row) reuse the exact
spacing classes of their surrounding siblings rather than introducing new values. No new spacing
token is needed.

`[data-tecponto-theme="light"]`; orange, red, green, blue, purple, amber stay constant across
themes. No new theme-specific styling is needed — every class this phase uses already resolves
correctly under both themes.
