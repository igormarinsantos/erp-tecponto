<objective>
Harden the deadline write path and prove the value reaches the two surfaces that already read it
but have never had anything to show: the public tracking portal and the print formats.

Purpose: the tracer opened the write path. Three things are still open. First, the deadline is a
delivery promise and must stop being editable at the same moment `pickup_date` and
`warranty_expiry` do (D-04), or a delivered OS's promise could be rewritten after the fact.
Second, `calculate_suggested_delivery` has sat unused since it was written — D-05 makes it the
source of the técnico's pre-filled suggestion, and this plan builds its backend half. Third,
DEADLINE-02 asks for the deadline on the tracking page and the print formats; those templates
already reference the field, so the work here is proving it end to end, plus the one missing
template line in the laudo técnico.

Output: the immutability lock widened by one tuple entry, a public duration helper in `stage_sla`,
the `get_service_order_deadline_suggestion` endpoint, the laudo's "Prazo estimado" line, and the
portal/print assertions inside `run_service_order_deadline_checks`.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Guest → `get_public_portal` (`allow_guest=True`) | Anyone holding a tracking token reads an OS projection with no session; every field added here is public by definition |
| Delivered Service Order → later `save()` | Any authenticated write path that reaches a delivered document could rewrite a historical commitment |
| Print context builder → rendered HTML | The print templates are handed a wide context dict; a wrong key exposes internal data on a customer-facing document |
