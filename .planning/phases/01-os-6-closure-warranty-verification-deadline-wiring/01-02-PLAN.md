<objective>
Prove the 90-day repair warranty boundary is really enforced by the engine, at the exact day it
flips, by running create → deliver → claim against real dates on a live site.

Purpose: WARR-01 is the last open OS.6 warranty item. The rule is implemented
(`_validate_warranty` in `policies.py` throws "Garantia vencida." once `warranty_expiry` is in the
past) and the existing check already covers a wildly-expired case (delivered 100 days ago, expired
10 days ago), but nothing has ever exercised the day the boundary actually flips. A rule that is
only tested far from its edge is a rule nobody has tested.

Output: day-89 / day-90 / day-91 boundary assertions added inside the existing
`run_warranty_delivery_checks`, plus three new result keys on its returned dict.
</objective>

Per D-01, extend the existing `run_warranty_delivery_checks` — do not write a new standalone check function. The fixtures, users, catalog service and `finally` cleanup this function already sets up are the whole reason to reuse it.

Insert the new block immediately after the existing expired-warranty assertion (the one ending with the "Motor aceitou retrabalho com garantia expirada." message and the follow-up `expired_normal` check-in, around line 2678) and before the line that switches `default_warranty_days` to 30. The engine cannot be time-travelled, so simulate the calendar the same way the existing expired case does — by back-dating delivery on a freshly created OS. For each of three cases, delivered 89, 90 and 91 days ago:

Create an isolated order with `_create_action_request_service_order(attendant)` and load it with `frappe.get_doc`. Compute `boundary_pickup = add_days(nowdate(), -N)` and force the delivered state with `db_set` of `workflow_state` "Entregue", `pickup_date` `boundary_pickup`, and `warranty_expiry` `add_days(boundary_pickup, 90)` with `update_modified=False` — the same one-line `db_set` shape the expired case uses. Deriving the expiry from the pickup date rather than hardcoding it is what makes this a real 90-day-window test rather than a date-arithmetic tautology.

Then attempt the claim as the attendant with `create_service_order_checkin`, passing the boundary order's own customer and device by `existing_name`, its own `reported_defect` verbatim (a different defect would be silently converted to a normal OS by `is_same_warranty_defect` and would prove nothing), `is_warranty` 1, `original_service_order` set to the boundary order's name, and the shared `photo_data` as `entry_photo`. Wrap it in the `blocked = False / try / except frappe.ValidationError: blocked = True` shape already used for the expired case.

Expected outcomes, which follow directly from the inclusive comparison in `_validate_warranty`: delivered 89 days ago means the expiry is tomorrow and the claim must succeed; delivered exactly 90 days ago means the expiry is today and the claim must still succeed, because the guard rejects only a strictly past expiry; delivered 91 days ago means the expiry was yesterday and the claim must be rejected. Raise `AssertionError` with a distinct Portuguese message per case when the observed outcome differs, following the file's existing message style.
