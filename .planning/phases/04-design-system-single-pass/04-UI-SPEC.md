## Spacing Scale

**Documented as-is, per D-02 — no new scale is introduced.** The codebase does not use the clean
8-point rungs (4/8/16/24/32/48/64) the generic template below suggests; it uses a base-4 scale with
several already-entrenched values that fall *between* those rungs. Treating those as "drift" and
correcting them to the nearest 8-point value would itself be exactly the redesign D-02 rules out.

| Value | Tailwind class(es) seen | Where it's load-bearing |
|-------|--------------------------|--------------------------|
| 4px | `gap-1`, `p-1` | icon-to-label gaps inside chips/badges |
| 8px | `gap-2`, `p-2` | compact control spacing (chip rows, sidebar item internals) |
| 12px | `gap-3`, `p-3` | `ContextMenu` item padding, `Sidebar` nav rows, `StatBar`/`Card` internals |
| 16px | `gap-4`, `p-4` | the single most common card/panel padding (`WizardCard`, `Modal` body, `Topbar` gaps) |
| 20px | `p-5` | `Card`/`MetricCard` padding, `PosScreen` root spacing |
| 24px | `gap-6`, `p-6` (rare) | large choice-card padding (`MicrostepChoiceCard` non-compact) |
| 40px / 44px | `min-h-10` / `min-h-11` | default interactive height (buttons, inputs) is 40px; `ContextMenu`/`OptionChip` items step up to 44px, matching the standard minimum touch target |

Exceptions for this phase: none beyond what's already listed above (all pre-existing). Do not
introduce `gap-5`/`p-7`/etc. new increments during the consistency pass; reuse the values already
in the table for any spacing decision the pass has discretion over.

## Typography

**Documented as-is, per D-02 — no new type scale is introduced.** Role→value mapping below reflects
actual dominant usage (measured via `grep -c` across `frontend/src`), not an invented ideal. The
"light visual consistency pass" (D-02c) audits screens *against* this table — flag a screen using an
unusual one-off size/weight for a role that already has a standard, don't invent a new size.

| Role | Size | Weight | Line Height | Notes |
|------|------|--------|-------------|-------|
| Body / default UI text | 14px (`text-sm`) | 400 (regular, no utility class needed — Tailwind base) | default (`leading-normal`, ~1.43) | Dominant across the entire app (281 uses in `App.tsx` alone) — this is the default text size for labels, table cells, form fields, helper copy |
| Meta / secondary label | 12px (`text-xs`) | 400 or 600 (`font-semibold` when it's a field label, e.g. `ChipGroup`/`CheckboxGrid` labels) | default | Timestamps, table headers (`uppercase text-tec-muted`), helper/hint text under inputs |
| Micro / badge | 11px (`text-[11px]`, arbitrary value) | 600 (`font-semibold`) | `leading-none` | `BadgeStatus` pill text, `kbd` shortcut hints (`Topbar`, `PosScreen`). Documented, pre-existing exception to the named scale — do not expand this arbitrary value to new contexts during the pass |
| Heading / section title | 18–20px (`text-lg` / `text-xl`) | 700 (`font-bold`, auto-applied by the global `.tp-display, h1, h2, h3, h4 { font-weight: 700 }` rule in `tailwind.css`) | `leading-tight`-ish, tight by default on headings | `SectionTitle`, `Modal` header (`text-lg`), card section headers |
| Display / page title & stat value | 24–36px (`text-2xl` → `text-4xl`) | 700 (`font-bold`) | tight | Page `<h1>` (`text-3xl md:text-4xl` in `PosScreen`), `MetricCard`/`StatBar` numerals (both carry `.tp-metric-value`, which forces `font-family: var(--tp-font-display)` + `font-variant-numeric: tabular-nums`) |

**Weight system in practice is 2 active weights + 1 implicit default:** regular/400 (implicit,
default body — no class), `font-semibold` (600, the dominant emphasis weight — labels, active states,
buttons), `font-bold` (700, headings and numeral emphasis, auto-forced onto `h1–h4`/`.tp-metric-value`/
`.tp-nav-label` by the global CSS rule). `font-medium` (11 uses total) and `font-normal` (2 uses) are
rare, pre-existing outliers — do not spread them further during the pass; converge toward
`font-semibold`/`font-bold` where a screen already drifted to `font-medium` for emphasis that should be
`font-semibold`.

## Color

Dark theme is the default (`:root`); `:root[data-tecponto-theme="light"]` overrides only the
surface/text family, never the 8 semantic/brand colors — accent, success, destructive, and the other
5 semantic tones are theme-invariant by design.

| Role | Token / Value | Usage |
|------|-------|-------|
| Dominant (60%) | `tec-bg` — dark `rgb(21 24 27)`, light `rgb(238 237 246)` | App background (`body`, `#tecponto-root`) |
| Secondary (30%) | `tec-panel` / `tec-panel-strong` / `tec-field` / `tec-sidebar` — dark family in `18–41` range, light family white/near-white except `tec-sidebar` (kept dark-graphite in both themes) | Cards, modals, sidebar, inputs/fields, table headers |
| Accent (10%) | `tec-orange` `rgb(254 80 0)` (same value in both themes) | **Reserved for:** primary CTA buttons (`Button variant="primary"`), the active/selected state of navigation items, tabs, chips, and choice cards (`OptionChip`/`OptionCard`/`ChipGroup` active state), the focus ring (`focus:ring-tec-orange/70`), the brand `shadow-glow`, the wizard stepper's "active step" ring/label, the small "required" dot next to field labels. Never use `tec-orange` for a merely-hovered (non-selected) state — hover states use `border-tec-orange/50` at most, never a filled background, to keep the accent legible as "this is the one selected/primary thing." |
| Destructive | `tec-red` `rgb(239 55 55)` (same value in both themes) | `Button variant="danger"`, `Toast tone="error"`, form/API error banners (`border-tec-red/30 bg-tec-red/10 text-tec-red`), `BadgeStatus` for "Reprovado"/"Orçamento expirado" |
| Success (secondary semantic) | `tec-success` / `tec-green` `rgb(104 184 122)` | Completed/approved states — `BadgeStatus` "Aprovado"/"Entregue", wizard stepper's "done" state, PDV sale-completed confirmation icon |
| Other semantic tones (already in the palette, used consistently) | `tec-blue` (info/notifications, customer avatar chip), `tec-amber` (pending/awaiting states), `tec-purple` (in-queue/waiting-on-parts), `tec-whatsapp` (WhatsApp affordance only) | Each has one narrow, consistent job already — do not repurpose during the pass |

Accent reserved for: primary CTA buttons, active/selected navigation and choice states, focus rings,
the brand glow shadow, the wizard's active-step indicator, and the required-field dot. Never "all
interactive elements" — secondary/ghost buttons and unselected chips stay on the neutral `tec-field`/
`tec-border` family.

## OS-vs-PDV Visual Consistency — Starting Evidence (D-05/D-06)

Concrete, evidenced comparison points found during this research (visual-only, per D-06 — none of
these are functional divergences):

1. **Semantic color tokens.** PDV (`PosScreen.tsx`, sampled in full) is 100% `tec-*` token-compliant.
   OS screens (`App.tsx`'s budget-decision UI, `ServiceOrderKanban.tsx`'s overdue indicator) use raw
   `emerald`/`rose`/`amber`/`red` Tailwind classes for the identical semantic meanings PDV already
   expresses with tokens. See "Known token drift" table above for exact locations — this is the
   single highest-value OS-vs-PDV alignment target found.
2. **Button variant discipline.** PDV uses `Button variant="danger"`/`variant="primary"` exclusively
   (no raw `className` color overrides). OS's budget-decision approve/reject buttons
   (`App.tsx:4631-4647`) override `Button` with raw `className="bg-emerald-600..."` /
   `className="border-rose-500/40..."` instead of using the existing `danger` variant for reject and
   `primary` (or a case for adding a `success` variant, planner's discretion) for approve.
3. **Status/badge pattern.** PDV has no per-screen custom badge — it defers entirely to `BadgeStatus`.
   OS's budget-decision card hand-rolls its own approve/reject/expired/pending pill markup instead of
