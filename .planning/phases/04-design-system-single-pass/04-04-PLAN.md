Required sections, in this order.

Opening statement of what the document is and what it is not: a description of the production design
system as of this phase, authoritative for how to style new work, and explicitly not a proposal.
Name the three source files it transcribes so a future reader knows what to re-check it against.

Tokens. Transcribe the custom properties from tokens.css into role-grouped tables: surfaces,
text, brand and semantic colours, fonts, radii, and the layout constants. Give each token its
literal RGB triple. Document the theme model honestly: the base block is the dark theme, the dark
attribute block repeats the surface and text family, and the light attribute block overrides only
that family while every brand and semantic colour stays theme-invariant. Call out by name the two
tokens whose light-theme value inverts relative to their dark value — this is the fact that made
the Prata swatch in plan 04-01 read differently per theme, and it is the single most surprising
thing in the token system.

Tailwind wiring. State how tokens.css becomes the `tec` colour namespace, and name the radius, font
and shadow keys tailwind.config.ts defines. State the rule that follows from it: style through
`tec-*` classes, never through a raw Tailwind palette family, and note that from this phase onward
the build enforces it.

Colour usage rules. Which role each semantic colour owns, and what the accent is reserved for —
primary CTAs, active and selected states, focus rings, the brand glow and the required-field dot —
together with the rule that a merely-hovered control never takes a filled accent background. Take
this from UI-SPEC's Color section, which is already verified.

Typography. The role-to-size-and-weight table from UI-SPEC, stated as observed dominant usage with
its measured basis, not as an invented ideal. Name the two active weights plus the implicit default,
and the global rule that forces bold onto headings and metric values.

Spacing and sizing. The base-4 values actually in use, including the off-8-point ones, with where
each is load-bearing. State plainly that the codebase does not use clean 8-point rungs and that
correcting it would be a redesign this phase deliberately did not do.

Component library. One row per export from src/ui/index.ts: name, import path, its one-line job,
and a usage example copied from a real call site that exists in the tree — cite the file and line
for each so a reader can verify it. Include the fifth Button variant plan 04-02 added. Add a short
subsection for the wizard-local primitives defined inside CheckinWizard.tsx, noting they are
token-compliant and design-system-conformant but not exported, so new screens should not import
them.

Established patterns. The error-banner shape, the empty-state and error-state copy templates, the
two-step destructive-confirmation shape, and the check-in wizard's 7-step structure as restructured
by plan 04-01, including the rule that the step count now lives in four arrays the build keeps
aligned.

Known debt, deliberately not fixed. Transcribe the UI-SPEC checker's logged flags: more than four
type sizes and more than two active weights; spacing values off the 8-point set; error states that
share the empty-state slot with no distinct treatment and no retry affordance; and the display and
body font variables currently resolving to the same physical typeface. For each, say why it was not
addressed — D-01 and D-02 lock this phase to documenting the existing system — so a future phase
inherits the list rather than rediscovering it.

Write in the same language as the rest of the repository's developer-facing documentation. Every

against the live file as you write it; do not copy a value from UI-SPEC or PATTERNS without
confirming it, because both were written before plans 04-01 through 04-03 changed several of them.
