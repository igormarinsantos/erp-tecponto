### Session & Privilege-Escalation Pattern (stack-specific pitfall, already root-caused in this repo)

| Practice | Mechanism | Why |
|----------|---------|-----|
| Never call `frappe.set_user()` directly in production code (or in new code at all, outside test fixtures) | Use the existing `as_user()` context manager in `tecponto_app/tecponto/permissions.py` | The exact failure mode is already documented in the function's own docstring: `frappe.set_user()` doesn't just swap `frappe.session.user`, it also overwrites `frappe.session.sid` with the plain username and wipes `frappe.session.data`. Since `frappe.session.sid` is precisely the value `frappe/auth.py` writes into the outgoing `Set-Cookie: sid=...` header, even a perfectly-restored `session.user` still ships a cookie matching no real session — the browser's *next* request gets rejected with "User None not found". `as_user()` only ever touches `session.user` plus the per-request permission caches (`role_permissions`, `user_perms`, `frappe.local.cache`), never `.sid`/`.data`. This is a root cause this project already found, fixed, and left a precise trail for — reuse it, don't rediscover it. Confidence: HIGH (primary source: this repo's own code + `CONCERNS.md`'s documented 10-call-site fix). |
| Prefer `ignore_permissions=True` on the specific `doc.insert()`/`doc.save()`/`frappe.get_doc()` call over any user-context switch, when the goal is only "bypass a permission check" (not "evaluate role-scoped filtering logic as a different identity") | Standard Frappe API parameter | If the actual need is "let this privileged action write a document regardless of the acting user's normal permissions" (e.g. system-triggered audit log write, notification record), `ignore_permissions=True` is the narrower, framework-native tool — it doesn't touch session state at all, so it can't reproduce the `set_user()` failure class even by accident. Reserve `as_user()` for the cases that genuinely need role-scoped query/filter logic evaluated as another identity (e.g. `is_restricted_technician()` checks, `part_request_query()`). Confidence: MEDIUM (framework-documented parameter; the "prefer this when possible" guidance is this researcher's synthesis, not an explicit Frappe recommendation). |
| Grep for `frappe.session.user =` (direct assignment, bypassing even `as_user()`) as part of the audit, not just `frappe.set_user(` | Manual grep, add to the same CI gate | A developer under time pressure can reach for direct session mutation as a "simpler" workaround to the very anti-pattern the CI gate blocks — the gate needs to catch the near-variant too, not just the exact function call. Confidence: MEDIUM (reasoned extrapolation, not observed in this repo's current code). |

### Background Jobs (relevant where notifications/audit-log/print jobs touch async work)

| Practice | Mechanism | Why |
|----------|---------|-----|
| Keep using `frappe.enqueue(..., queue="short", ...)` for notification sends (WhatsApp), bypassed synchronously under `frappe.flags.in_test` | Already implemented in `notify.py` | This is the correct existing pattern — Frappe's three queues (`short`/`default`/`long`) map to 300/300/1500-second timeouts by default; notification sends belong on `short`. The test-mode synchronous bypass (`if frappe.flags.in_test: send(...); return True`) is exactly right for keeping the integration harness deterministic without waiting on a real worker. Keep this pattern for any new async work introduced this milestone (e.g., if the audit-log write becomes async, or a print-job queue is added for Coolify). Confidence: HIGH (Frappe docs confirm queue/timeout defaults; the test-bypass pattern is already correct and working in this repo). |
| If a new async job is added this milestone (e.g., bulk warranty-expiry sweep, PDV/caixa daily close job), respect the ~500-pending-job soft cap and choose queue by realistic runtime, not by default habit | `frappe.enqueue(queue=...)` | `frappe.enqueue` starts failing once ~500 jobs are pending in a queue; a background job whose realistic runtime exceeds a queue's timeout will be silently killed mid-work with no exception in the calling request (the request already returned). For anything touching cash/financial state, prefer synchronous execution unless there's a proven need for async — silent mid-job termination on a caixa-close job is a much worse failure mode than a slightly slower request. Confidence: MEDIUM (framework behavior from Frappe forum/docs; not yet exercised by a caixa-specific job in this repo). |
| Verify `frappe.in_test` vs `frappe.flags.in_test` usage is consistent going forward | v16 migration note | v16 introduces `frappe.in_test` as the preferred form (`frappe.flags.in_test` still works but is the older idiom per the same migration wiki that deprecates `FrappeTestCase`). Not urgent to change existing working code, but use the newer form in anything newly written this milestone to avoid mixing idioms. Confidence: MEDIUM (sourced from the same v16 migration wiki; not independently re-verified against a second source). |

### Workflow State Machine (relevant to the 6 lifecycle gates + new "OS-wide deadline" field)

| Practice | Mechanism | Why |
|----------|---------|-----|
| Never write `workflow_state` via raw `frappe.db.set_value()`/`doc.db_set()` in production code — only through the workflow engine (`apply_workflow` / normal `doc.save()` with the Workflow doctype active) | Confirmed current practice | Audited this repo: **every** raw `workflow_state` write via `frappe.db.set_value()`/`db_set()` found in the codebase is confined to `test_frontend_api.py` test fixtures (e.g., simulating "warranty expired 100 days ago" by backdating `pickup_date`/`warranty_expiry`), which is a legitimate, narrowly-scoped use for time-travel test setup. No production code (`service_order/*.py`, `frontend/api.py`) does this. **This is already correct — keep it that way**, and treat any new PR that raw-writes `workflow_state` outside a test fixture as a review blocker, because it's precisely the pattern that bypasses Frappe's own permission-transition validation gap (see Pitfalls: workflow permission checks don't validate that the current DB value is itself a permitted state before allowing an edit). Confidence: HIGH (direct grep audit of this repo, this session). |
| When defining the new OS-wide `estimated_delivery` field (technician-set, single deadline), keep it a plain document field with its own validation — do not model it as a workflow *state* | Doctype field, not `workflow_state` value | The workflow states already encode the 5-stage lifecycle (Entrada → Diagnóstico → Aprovação → Execução → Retirada); a delivery deadline is orthogonal data attached to whichever state the OS is currently in, not a state itself. Conflating the two would multiply the workflow's state count and risk hitting Frappe's documented multi-role-per-state bug (see Pitfalls) unnecessarily. Confidence: HIGH (architectural reasoning grounded in this repo's existing `estimated_deadline`-per-line pattern already working the same way). |
| Audit the Workflow doctype definition for Service Order for any state with **more than one role** permitted to edit | Manual check of the Workflow doctype's transition/state-role config (Desk UI or fixture JSON) | Frappe has a long-standing, still-open bug where if multiple roles are configured to edit a document in a single workflow state, only the *first* configured role is actually granted edit rights — the others silently can't edit despite being configured to. If Service Order's workflow has any state where e.g. both Atendente and Gestor should be able to edit, verify empirically (log in as the second-listed role, attempt the edit) rather than trusting the config. Confidence: MEDIUM (documented as a known, longstanding Frappe/ERPNext GitHub issue; not yet confirmed against this repo's specific Workflow config in this research pass — flag for the audit phase to check directly). |

### POS/PDV and Caixa Audit Patterns (custom-built, not ERPNext's stock POS module)

| Practice | Mechanism | Why |
|----------|---------|-----|
| Audit cash reconciliation with a **mixed-transaction-type** scenario in one register session, not per-transaction-type tests | New end-to-end test: open one `Tecponto Cash Session`, run a cash sale + card sale + trade-in-credit-applied + no-charge-warranty-completion, then close and verify the closing total reconciles | Financial reconciliation logic reviewed/tested per transaction type in isolation structurally cannot catch cross-type interaction bugs (rounding, double-counting, a missed payment-method bucket) — this is exactly the failure mode ERPNext's own historical POS cash-reconciliation issues (`erpnext#7582`, `erpnext#16616`) illustrate as a known category, even though this app's caixa module is custom-built and doesn't share that code. Treat those issues as precedent for *what to test defensively*, not as bugs that could recur verbatim. Confidence: MEDIUM (ERPNext issues are historical/version-specific precedent for the failure category, not a direct code dependency of this app's custom caixa module). |
| Explicitly break out cash/card/trade-in-credit/warranty-no-charge buckets in the close summary UI and in the audit test's assertions | `cash.py` closing logic + frontend close screen | Staff need to self-verify the close total against physical cash on hand; a single blended total makes end-of-day reconciliation disputes undebuggable, and a test that only checks the blended total (not each bucket) can pass while a specific bucket is wrong and happens to cancel out. Confidence: MEDIUM (UX/testing reasoning, not sourced from an external precedent). |
| Since PDV/caixa are custom doctypes (`Tecponto Cash Session`, `Tecponto Cash Movement`), audit `frappe.get_all()` calls in `pos.py`/`cash.py` for missing `limit_page_length`, same as already flagged for `api.py` generally | Manual grep + `CONCERNS.md`'s existing pattern | `CONCERNS.md` already flags unbounded `get_all()` calls as a known pattern in `api.py`; PDV/caixa modules haven't been audited yet and are equally likely to have the same gap, especially on any endpoint that lists historical cash movements or sales for a session. Confidence: MEDIUM (extrapolation from a documented pattern in a sibling module, not yet confirmed in `pos.py`/`cash.py` specifically). |

## What NOT to Use

| Avoid | Why | Use Instead |
|-------|-----|--------------|
| `frappe.tests.utils.FrappeTestCase` for any new pytest-style test class | Deprecated in v16, scheduled for removal in v17 (official Frappe GitHub wiki) — writing new tests against it creates immediate tech debt | `from frappe.tests import IntegrationTestCase` (DB-touching tests) or `UnitTestCase` (pure in-memory logic) |
| `frappe.set_user()` anywhere in production code, or as a "quick fix" in new audit-log/edit-endpoint code | Corrupts `frappe.session.sid` and `.data`, producing session death on the user's *next* request — this project already suffered this exact bug across 10 call sites and fixed it once | The existing `as_user()` context manager in `permissions.py`, or `ignore_permissions=True` when only a permission bypass (not identity-scoped filtering) is needed |
| Frappe's built-in `track_changes` (Version doctype) as the "audit log" for the new editable OS fields (contact, device credential, CPF) | Captures the entire document diff, including cost/margin/credential fields if they live on the same document — leaks through Frappe's own generic Version/Activity Log UI, which the custom `contains_sensitive_field()` API guard does nothing to protect (that guard only covers the custom `frontend/api.py` response path) | A purpose-built, field-scoped audit doctype/child table that only stores the three fields being made editable, served through the same guarded API surface as everything else |
| ERPNext's built-in POS Invoice / POS Closing Entry module as a reference implementation to copy from for caixa audit fixes | This app already deliberately built custom `Tecponto Cash Session`/`Tecponto Cash Movement` doctypes instead of using ERPNext's stock POS module — pulling in ERPNext POS patterns or doctypes now would be a parallel, inconsistent system, not a fix | Keep all caixa/PDV fixes inside the existing custom `cash.py`/`pos.py` modules; use ERPNext's historical POS GitHub issues only as a checklist of failure categories to test for, not as code to port |
| A generic "patch any Service Order field" endpoint for the new editable-fields feature | Structurally reopens the same class of bypass risk the 6 workflow lifecycle gates and cost guard exist to prevent — a `field_name`/`value` pair parameter is one bad frontend call away from touching pricing or workflow-adjacent fields | Three explicit, narrowly-scoped handlers (or one endpoint with a hard-coded, non-configurable field allow-list) for contact info, device credential, and CPF respectively |

## Alternatives Considered

| Category | Recommended | Alternative | Why Not (for this milestone) |
|----------|-------------|-------------|---------|
| Async execution for a caixa-close/warranty-sweep job | Synchronous by default; async only if proven necessary | `frappe.enqueue()` on `default`/`long` queue | A background job that silently exceeds its timeout returns no error to the caller — for anything touching cash/financial state, the failure mode of "request took 2 extra seconds" is strictly safer than "job died mid-write with the request already reporting success." Revisit only if caixa-close volume genuinely requires async at pilot scale (unlikely for a single-store pilot). |
| Audit log storage | Purpose-built doctype/child table | Frappe's native `track_changes` (Version doctype) | See "What NOT to Use" — leaks cost/credential data through an unguarded native channel that the existing API-layer guard doesn't cover. |
| New pytest-style unit tests for warranty boundary logic | `frappe.tests.UnitTestCase`/`IntegrationTestCase` (v16-current) | `frappe.tests.utils.FrappeTestCase` | Deprecated, removed in v17 — would be dead-on-arrival tech debt for a system whose whole motivation this milestone is *reducing* accumulated confusion, not adding more. |
| PDV/caixa cash-reconciliation implementation | Continue with existing custom `Tecponto Cash Session`/`Tecponto Cash Movement` doctypes | Migrate to ERPNext's built-in POS Invoice / POS Closing Entry | Out of scope for a stabilization milestone — a mid-flight module swap on financial code is exactly the kind of change this milestone exists to *avoid* introducing; audit and harden what exists instead. |

## Stack Patterns by Variant

**If a new async job is introduced for anything touching money (caixa close, warranty batch expiry, refunds):**
- Run it synchronously in the request/response cycle, or make the async path idempotent and re-checkable from the UI (a "job status" the staff can see and retry)
- Because a silently-timed-out or silently-failed background job on financial data is worse than a slower request — there's no natural place in this app's current architecture for staff to notice a failed async job

**If the new editable-fields feature needs to log "who changed what, when":**
- Use a dedicated child table or doctype scoped exactly to `contact_name`, `contact_phone`, `device_access_credential` (masked reference only), `customer_name`, `customer_cpf`
- Because the audit trail needs to be read through the same role/sensitivity guard as everything else, which only works if it's a first-class part of this app's own schema, not a side effect of a generic framework feature

**If audit work turns up more `frappe.set_user()` instances in PDV/trade-in/caixa (very likely, per the CI-gate rationale above):**
- Fix each one with the existing `as_user()` context manager, exactly as done for the OS module's 10 call sites
- Because it's already a proven, mechanical fix — don't design a new pattern, reuse the one that worked
